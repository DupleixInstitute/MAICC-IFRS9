# Copilot review of MAIIC EIR Engine Specification v4

Date: 12 October 2026. Repository: `DupleixInstitute/MAICC-IFRS9`. Branch reviewed: `eir_revenue_recognition`. Specification reviewed: `docs/MAIIC_EIR_Engine_Specification_v4_2026-10-07.md`.

Read against `docs/REVIEW_BRIEF_Spec_v4_for_Codex_2026-10-12.md`. The specification was not edited. This review is limited to the repository evidence named in the brief: `docs/bootstrap/`, `docs/build-files/` and `app/Services/Eir/`.

## Findings

| Section | Text quoted | Issue | Evidence | Suggested correction |
|---|---|---|---|---|
| 3.7 | "The fee ledgers agree to the trial balance ... QuickBooks 4206 = E-Banker 4215 + 4216 + 42019, plus ... suspense reversal ... plus 259,317,000 of fees presented as EIR interest" | The GL reconciliation is checkable in-repo, but the QuickBooks bridge itself is not in the repository. The claim is therefore not evidence-backed here and should be labelled as a Finance-supplied bridge, not as a proven fact. | `docs/build-files/fee_gl_recon_2026-10-11.py` matches the GL spools to the trial balance and `app/Services/Eir/FeeGlReconciliationService.php` does the same check month by month. There is no QuickBooks workbook or source data in `docs/bootstrap/` or `app/Services/Eir/` that reproduces the 4206 mapping. | Keep the GL-to-trial-balance proof as Proven. Label the 4206 bridge and the 259,317,000 presentation entry as Finance's external reconciliation until the workbook or supporting journal is committed under `docs/bootstrap/` or a source file in the repo. |
| 3.8 | "Status code H means written off and closed ... a write-off must never be read as a collection" | The repository contains no status-H logic, no write-off classification rule in the EIR engine and no explicit mapping of status H to write-off in the code. This claim is not proven by the repo evidence named in the brief; it is a Finance interpretation that needs a standalone confirmation. | `database/seeders/EbankerQuerySeeder.php` lists `GL_05` and `RS_02g` write-off and closure-related queries, but `app/Services/Eir/` contains no `status H` rule, no `write-off` service and no loan-level classifier for H. The brief itself warns that the reading of status H is one of the claims the evidence does not support. | Reword as "Finance has advised that status H means written off and closed" until a query or service proves it. Add the rule as a governed condition or keep it as a pending manual control with the evidence file and approval trail attached. |
| 3.9 | "Reschedules can be rebuilt from E-Banker's own tables ... the stored loan books are not a register" | This is described as a fact, but the repository evidence shows only the query register for the rebuilt data, not a loader or a working reschedule register in the EIR engine. The implementation is still missing. | `database/seeders/EbankerQuerySeeder.php` contains `RS_02a` through `RS_02g`, but there is no corresponding service logic under `app/Services/Eir/` that rebuilds or consumes the reschedule history. The review brief explicitly says the reschedule register of 3.9 is not built yet. | Mark 3.9 as a planned design, not a proven fact. Add the actual build step and the acceptance rule when the historical reschedule logic is implemented, and keep the validation evidence with the matching `RS_02*` rows. |
| 4.2 | "every Governance Centre setting ... and where it stands" | The governance catalogue is incomplete relative to the design described in 7.8, and the fee source precedence that the spec says is a decision is absent from the actual setting list. | `app/Services/Eir/GovernanceService.php` has `fee_gl_reconciliation` but no `fee_source_precedence`, no `GL_04` batch-link setting and no fee-source precedence rule. `database/seeders/EbankerQuerySeeder.php` names `GL_04a` and `GL_04b`, but there is no code in `app/Services/Eir/` that uses them as a governed precedence control. | Add the missing governance item and make the effective precedence explicit in the catalogue. Until it exists, the spec should say that fee-source precedence is a to-build decision and not a settled Governance Centre setting. |
| 7.1 | "The old `GlInterestImportService`, which skipped annual rows, is retired" | The repository shows the old service is still present and still contains explicit annual-summary handling. The claim is therefore false as written. | `app/Services/Eir/GlInterestImportService.php` is still in the repository and explicitly documents the "annual summary rows" logic. It is not retired in this branch. | Replace the statement with a more precise one such as: "The legacy Extract C importer remains in the repo for evidence and comparison, while the current engine reads the ledger directly and uses the GL interest postings only as a reconciliation input." |
| 7.8 | "six sources, one source of record (the GL posting), five delivery routes" | The design is described as if implemented, but the repository does not show a single source-of-record rule or a batch-link for the fee rows. The declared precedence and linkage are still design work, not working code. | `app/Services/Eir/GovernanceService.php` does not define `fee_source_precedence`; `app/Services/Eir/FeeGlReconciliationService.php` compares imported fees to GL totals but does not enforce precedence, and no `GL_04` linking code exists. The review brief also lists "fee_source_precedence" and "the GL_04 batch link" as still not built. | Describe this section as a target design or proposal, not as an implemented control. The setting and the batch linkage should be added to the policy before the spec presents them as the source of record. |
| 7.8 | "about 44 percent of 2025 fee income never touched a loan account" | The figure is directionally useful, but the repo evidence demonstrates that it depends on a matching method with named caveats and should be labelled as a current estimate rather than a settled accounting fact. | `docs/build-files/fee_gl_recon_2026-10-11.py` matches each spool line to the loan ledger by date and amount and then reports a summary. The comment in `app/Services/Eir/FeeGlReconciliationService.php` is consistent with a reconciliation estimate, not a final accounting conclusion. The script also does not separate closing vouchers or ambiguous matches before deriving the ratio. | State the figure as "approximately 44 percent under the current GL-vs-ledger matching method" and keep the caveat in the text. Add the exact matching rules and exclusions used to produce the percentage before calling it a proven fact. |
| 7.8.4 | "A type-301 line in a batch that also credits a fee GL, or whose narration names a fee, is instead the fee capitalised into the loan" | This is the most acute implementation error in the fee design: it treats any fee-bearing advance as a fee, not a gross drawdown containing fees. The repo evidence keeps the gross tranche and the fee as separate inputs, and the spec's rule would collapse them. | `app/Services/Eir/FeeImportService.php` imports fees separately from the loan transaction stream, and `app/Services/Eir/EirRevenueService.php` classifies cash received separately from derecognition and write-offs. The fee and drawdown are treated as distinct facts in code, not as one combined classification. | Separate the gross drawdown from separate fee debits. Keep the advance at its original tranche date and classify the fee as a fee by an independent voucher or GL leg. Do not classify a fee-bearing drawdown batch as an automatic fee without reconciling the underlying voucher. |
| 2; 3.1 to 3.6; 6; 7.2 to 7.7; 8; 9 | "Reviewed for evidence against the repository; no direct implementation issue found beyond the items above" | These sections are broadly consistent with the code and data dictionary once the unsupported fee, H-status and reschedule claims are excluded. They are mostly design descriptions, and they do not create a repo-backed contradiction on their own. | `app/Services/Eir/GovernanceService.php`, `app/Services/Eir/ContractMasterImportService.php`, `app/Services/Eir/ReferenceRateImportService.php`, `app/Services/Eir/TrialBalanceMovementService.php`, `app/Services/Eir/FeeImportService.php`, and `database/seeders/EbankerQuerySeeder.php` together support the general design flow and the governance and import model. | Keep these sections as design text and remove any wording that implies a proven fact when the repository only shows the raw query register or a planned design step. |
