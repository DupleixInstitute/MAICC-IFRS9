## 4. Data Onboarding

Data enters by two doors. The file imports (loan book, clients, collateral, credit loss data, the EIR extracts, the SICR lists, the macro series) are uploaded on their screens, checked against one column-spec registry and loaded by their importers; they record progress in the `imports` table, which records the `kind` of each import (chapter 3.3), visible under Customer & Loan Data, Imports & Feeds, on the Imports tab. The E-Banker packs, the trial balances and the take-on workbook enter by the landing zone (4.6 to 4.8): every row is landed verbatim with its hash and gate results, and the loan book and the EIR inputs are built from the landed rows.

### 4.1 Loan book import

There are two loan book paths, both under `app/Http/Controllers/LoanBookController.php`. Both run the import check of 4.3 first (spec keys `loan-book` and `loan-book-ebanker`) and refuse the whole file, with every problem listed by row, before anything is written.

The CSV import (`import()`) accepts a CSV, a portfolio, an import type (`legacy` for the standard layout, `custom` for Match columns) and, for Match columns, the column mapping, which the check reads through. It creates an `imports` row of kind `loan_book` with status `pending` and runs `app/Imports/LoanBooksImport.php`. That importer reads in chunks of 500 rows, validates that `customer_id` and the value and maturity dates are present and parseable, writes each chunk with an upsert keyed on customer, portfolio, reporting period and contract, and appends rejected rows to `storage/app/public/failed_imports/loan_books_exception_{import_id}.csv` with the reason. The import events move the status from `pending` to `processing` to `completed` or `failed` and keep `records` and `failed_records` in step. The IFRS 9 stage of every imported row is set by `app/Services/Eir/StagingClassifier.php` against the approved `staging_thresholds` row in force at the period end; with no approved row in force the import stops and names what is missing (chapter 5.2).

The E-Banker grouped export import (`importGroup()`) accepts the positional core banking CSV, stores it under `temp-imports` and dispatches `app/Jobs/ProcessLoanImportJob.php` through `app/Services/LoanImportService.php`. The job parses the two E-Banker layouts, expands scientific-notation account numbers, creates or updates clients, upserts `loan_books` in batches of 500 and computes the stage inline from the arrears columns. It records `failed_records` as total rows minus imported rows and does not write a failed rows file. A month built from the landing zone (4.6) does not use either path.

### 4.2 Collateral and client imports

`CollateralController::importCollateralRegister()` mirrors the loan book path with `app/Imports/CollateralRegisterImport.php`, an exception file named `collateral_register_exception_{id}.csv`, and the same status transitions; a mapped file is checked and loaded through its mapping. Client imports (`ClientsController::import()`) use `ClientsImport` and set `failed_file_path` so the Imports tab can offer the download. Both run the import check first (spec keys `collateral` and `clients`). The collateral type is a text code (chapter 3.3).

### 4.3 Sample files, column guides and the import check

Since 13 October 2026 every file import is described once, in `app/Support/Imports/ImportSpecs.php`: the title, numbered instructions, notes, the format uploaded, how headings are read, and each column with its type, whether it is required, its format, allowed values, range and a sample. The same entry drives four things, so the screen, the template and the validation cannot drift apart:

- the sample file in exactly the format the import reads (`ImportTemplateBuilder::template()`: CSV, TSV, an XLSX layout for the trial balance, or a sample `manifest.json` for an E-Banker pack);
- the XLSX column guide (`ImportTemplateBuilder::guide()`: the instructions, every column with its type, required flag, format and allowed values, and the sample rows);
- the instructions panel on the import screen (`resources/js/Components/Imports/ImportSpecPanel.vue`, reading the spec as JSON);
- the check (`app/Support/Imports/ImportSpecValidator.php`), which reads the file the way its importer does and tests the headings (every required column present, none twice) and every row (a value in each required cell, the type, the allowed values, the range, no key repeated). It fails closed: an error on any row refuses the whole file and the importer is not called; warnings (a value the importer folds, a repeat it is built to skip) are listed without refusing. The row-by-row result (`ImportCheckResult.vue`) says what is wrong and how to fix it.

`app/Http/Controllers/ImportTemplateController.php` serves them under the `import-templates.*` routes, each keyed by the spec key: `import-templates.download` (the sample file), `import-templates.guide`, `import-templates.spec` (JSON for the panel) and `import-templates.check` (POST; tests a chosen file and writes nothing: the Check file button). The older `import-samples.show` route serves the same sample files for the keys it always had.

The registry covers 21 imports: `clients`, `loan-book`, `loan-book-ebanker`, `collateral`, `credit-loss-data`, the seven EIR intake types (`eir-contract-master`, `eir-schedule`, `eir-fees`, `eir-contract-transactions`, `eir-gl-interest`, `eir-reference-rates`, `eir-disbursements`), `trial-balance`, `takeon`, `ebanker-pack`, `sp-grades`, `sicr-groups`, `sicr-items`, `macro-series`, `rbm-policy-rate` and `imf-weo`. The take-on workbook, the E-Banker pack and the S&P grades workbook have no Check file endpoint: they run their own gates or preview (4.6, 4.8, chapter 5.3), and their results are shown in the same row-by-row form. The EIR intake types are checked by `EirIntakeController` on the mapped rows (4.5).

### 4.4 The mapped file reader

`app/Services/Imports/MappedFileReader.php` is the reader for every EIR extract. Its behaviour matters for data quality:

- File type is detected from the first bytes (zip signature for xlsx, compound document signature for xls), never from the extension. CSV delimiters are sniffed from the first line.
- Headers are normalised to lowercase snake case. The mapping is a hard-coded alias table per import type (`app/Imports/ContractMasterImport.php`, `ContractTransactionImport.php`, `GlInterestImport.php`, `ReferenceRateImport.php`, `DisbursementImport.php`) overlaid by saved rows in `import_mappings`, where the saved rows win. Required fields that remain unmapped stop the import with a named error. Unmapped source headers are reported, not dropped.
- Contract ids are always canonicalised through `app/Support/ContractId.php`.
- Dates: a numeric value between 20,000 and 80,000 is treated as an Excel serial; otherwise the declared format is tried and only accepted if it round-trips; otherwise a general parse is attempted; otherwise the value becomes null and the row is reported. This exists because Extract B delivers actual rows as text dates and scheduled rows as serials, and Extract A mixes both in one column. For reference rates and drawdowns the declared format is dropped, so a date the file wrote ambiguously is refused rather than re-read.
- Numbers: thousands separators, non-breaking and zero-width spaces are stripped, and accounting negatives in parentheses are honoured.
- Column profiling only suggests `date` or `number` types when at least ninety percent of sampled values agree and, for numbers, when at least one value carries a decimal or thousands mark, so account numbers stay text. Percent is never guessed.

Import types and their required fields (`MappedFileReader::REQUIRED_FIELDS`): `contract_master` (contract id only, because the delivered Extract A column set is still being confirmed), `schedule` (contract id, due date, principal due, interest due), `fees` (contract id, fee type, amount), `contract_transactions` (customer id, contract id, sub account, date, type, principal and interest components, total, scheduled or actual flag, GL posting reference), `gl_interest` (contract id, period year, period month, interest income posted), `reference_rates` (effective date, rate) and `disbursements` (contract id, disbursement date, amount).

### 4.5 EIR intake

`app/Http/Controllers/EirIntakeController.php` drives the upload screen. `analyze()` profiles the file and proposes a mapping. `saveTemplate()` stores the mapping in `import_mappings`. `import()` reads the file synchronously first so mapping errors fail immediately, runs the import check on the mapped rows (any error refuses the file and nothing is queued), then creates an `imports` row named `EIR {type}: {file}` and dispatches `app/Jobs/ProcessEirImportJob.php`. The job routes the rows to the matching service, writes `failed_imports/eir_exception_{import_id}.csv` on the public disk with contract, status and reason columns, records the outcome in `audit_logs` under the action `EIR Intake Import`, and deletes the temporary upload. Only held and skipped contracts count as failures; notices about rows that loaded (incomplete terms, restatements) go into the file but not into the failure count.

| Extract | Service | Destination | Notes |
|---|---|---|---|
| A, contract master | `app/Services/Eir/ContractMasterImportService.php` | `contract_eir`, fee lines into `contract_fees` | Never rewrites a locked contract. Never sets `instrument_type` from the file. Merges the duplicate rows the delivered file carries (each facility appears twice); two stated values that disagree reject the facility and name the field. An unrecognised repayment frequency is reported, not defaulted. Arrangement and legal fee columns become PENDING fee lines with a deterministic external id so monthly redelivery does not double-create them. |
| B, transactions | `app/Services/Eir/ContractTransactionImportService.php` | `SCHEDULED` rows to `contract_remaining_cashflow_schedule` through `RemainingScheduleImportService`; `ACTUAL` rows to `eir_actual_transactions`; non-zero fee components to `contract_fees` | Rows whose contract is not on the loan tape are held. Any other flag value is a conflict. |
| Original schedules | `app/Services/Eir/ScheduleImportService.php` | `contract_cashflow_schedule` version 1, source `IMPORTED` | Per-contract rejection: existing schedule, missing or duplicate due dates, or scheduled principal more than one percent away from the drawn amount. |
| Fees | `app/Services/Eir/FeeImportService.php` | `contract_fees` | PENDING lines for classification; a line with a source and external id already held is not created again. |
| C, GL interest | `app/Services/Eir/GlInterestImportService.php` | `gl_interest_postings` | Annual control rows (`PERIOD_MONTH = 0`) are dropped. A changed amount for an existing key is applied as a named restatement. Signs are stored as delivered. |
| File C, reference rates | `app/Services/Eir/ReferenceRateImportService.php` | `reference_rate_series` | Dates must rise down the file; rates are percentages. |
| Drawdowns | `app/Services/Eir/DisbursementImportService.php` | `contract_disbursements` | One row per tranche; every amount above nil. |

The trial balances are not an intake type: they land through the landing zone (4.7).

### 4.6 The E-Banker landing zone

The E-Banker extracts arrive as packs: a folder of CSV files plus `manifest.json` naming each file, its query id and version, its rows and SHA-256, and the date format. `app/Services/Ebanker/PackLandingService.php` is the one door for every route:

| Route | How a pack arrives | Code |
|---|---|---|
| 1, manual | A zip uploaded on Imports & Feeds, E-Banker Loads (Load a pack, with a Check only option that runs the gates and keeps nothing), or `php artisan eir:land-pack {folder} [--dry-run]` | `EirFeedController::land()` (`eir-feed.land`), `LandEbankerPack` |
| 2, folder | A pack dropped in the feed folder (`EBANKER_FEED_FOLDER`), landed by `eir:poll-feed-folder` | `PollFeedFolder` |
| 3, API | The export script posts the zipped pack with a bearer token to `/api/ebanker-feed/pack` (`ebanker-feed.api`); it is unzipped into `storage/app/ebanker-inbox` and landed by `eir:poll-feed-folder --also-route-3` | `routes/web.php`, `FeedZip` |

Routes 4 (a direct database connection) and 5 (a vendor feed) are named in `PackLandingService` but not built. Every zip entry name is checked before anything is written (`FeedZip`): a name that would climb out of the target folder is left out and named on an upload, and refuses the whole pack at the API.

The service reads the manifest and runs the gates (`app/Services/Ebanker/PackGates.php`): every file named exists, its SHA-256 and row count match, its query id and version are in the register (`ebanker_queries`), every date parses in the stated format, every amount parses, the key is unique, and, across the files, every ledger account is in the master, the balance history ties to the ledger and every in-scope account has its month-end row. It then lands every row of every file verbatim as JSON in `ebanker_raw_rows`, as a new version where the content differs from the version held and never as an overwrite, and records the load with its gate results and watermark. A gate failure quarantines the pack: the rows are kept against the load so the refused file can be opened, and no reader sees them. A pack already landed is recognised by its manifest hash.

`app/Services/Ebanker/LandingZoneReader.php` is the only reader. It returns the current version of each row of landed loads, grouped into the logical tables of the spec (ledger, loan book runs, balance history, account, loan and rate masters, status history, charges, GL master, trial balance). `ledgerByAccount()` leaves the Mega Farm ledger (`MF_03`, every row of which is on the programme GLs 1050301 to 1050307) unread unless it is asked for (`withMegaFarm`), so the whole-ledger screens do not decode some 300,000 rows only to drop them.

What is built from the zone:

- The loan book: `app/Services/Ebanker/LoanBookBuildService.php` (`eir:build-loan-books {from} {to} [--method=]`, or Loan Book Builds on Imports & Feeds) by method A (the stored E-Banker run), B (derived from the ledger) or C (the printed report), the method in force being the governed `loan_book_build_method`. A build is proposed by one person and approved by another (`loan_book_builds`), prints every difference first, never restates a locked period, and never touches the stage, PD, LGD, FLI or ECL columns. Days past due are counted on the governed `dpd_basis`, read against E-Banker's instalment chart in force at the month-end (`InstalmentChartHistory`, chapter 5.2), and a balance still owed after maturity is overdue from maturity. The build reads the ledger once per build and slices it per month.
- Write-offs: `app/Services/Ebanker/WriteOffClassifier.php` decides which credits to a loan account are write-offs, not collections: transaction type 300; a credit in a batch whose other leg debits the write-off GL 1064 (read from `GL_05`, `GL_03` and `M09_01`); or an ACCOUNT CLOSURE in a TRF batch on an account whose status is H. The loan book build, the contract inputs and the EIR ledger cash all ask it, so the three agree. Write-offs that are not on the loan account go through the governed register (EIR Data, Write-offs; chapter 6).
- The EIR inputs: `ContractInputsBuildService` (contract master, PLR series, origination fees, interest posted, actual transactions, drawdowns, and the scheme settings with `eir:load-schemes`), `EirLedgerCashService` (`eir:load-ledger-cash`), `GlFeeBuildService` (`eir:build-gl-fees`, the GL fee route, with unplaced legs held in `fee_gl_unassigned`) and the restructure candidates (`eir:restructure-candidates`). Chapter 6 describes them.

A reporting period is locked or unlocked with a reason from Imports & Feeds, Periods Built (`eir-feed.lock-period`) or with `eir:lock-period {period} --reason= [--unlock]`; a locked period is never restated by any writer (chapter 5.8). Landing, building, approving and locking need `eir.govern`; viewing needs `eir.view`.

`php artisan eir:bootstrap --with-client-inputs` lands every pack committed under `docs/bootstrap`: packs 1 and 2 (the root `manifest.json`), each `ebanker-pack-*` folder (packs 3 and 5 to 9) and each zip under `docs/bootstrap/packs` (pack 4), then the take-on workbook and the trial balances, each through the same gates; a committed pack or trial balance that fails its gates stops the bootstrap. `docs/bootstrap/README.md` lists every file received and why any is not landed.

### 4.7 Trial balances

Finance's monthly E-Banker trial balance enters by the landing zone through `app/Services/Ebanker/TrialBalanceLandingService.php`, from EIR & Revenue Recognition, EIR Data, Trial Balances (`eir-trial-balances.index`; the upload, `eir-trial-balances.upload`, takes an xls or xlsx file, the basis, and optionally the period and sheet, and needs `eir.govern`) or from `php artisan eir:import-trial-balances {directory} [--afs=] [--sheet=] [--period=]`, which lands every `*.xls` file of a folder and, with `--afs`, the pre-closing December sheet of the AFS bridge workbook.

Each file is a load of its own in `ebanker_loads` (route `TRIAL_BALANCE_FILE`, the file's SHA-256 as the hash, so a file already landed is recognised and not loaded twice). The gates are the importer's own rules (`TrialBalanceImportService::read()` and `assertTies()`), run before anything is written: the period is known (from the file's stamp or as supplied), rows were found (only `code...title` rows are data), every Debit and Credit cell is a number, debits equal credits, and the file's grand total ties to the rows, each within one cent. A file that fails is quarantined with its rows kept. Each GL line is a raw row under query `TB_01`, keyed by period, basis and GL code, and versioned when a re-delivered file changes it.

`derive()` then writes `gl_trial_balance_lines`, the GL side of the reconciliation, from the current landed `TB_01` rows. It replaces only the months and bases the zone holds: within such a month a line the zone no longer holds is removed, so the month is exactly its landed file, but a month the zone does not hold (loaded before the landing zone existed) is left as it is, so landing one month from the screen never empties the others. With nothing landed it changes nothing. The screen lists the months held by basis and every load with its gates.

### 4.8 The take-on workbook

The take-on schedules (Finance's workbook as received, and the mapping workbook with the proposed E-Banker account per facility, Finance's tick and the fee columns) are landed by `app/Services/Ebanker/TakeonLandingService.php` from Imports & Feeds, Take-on Blocks (`eir-takeon.upload`) or `php artisan eir:land-takeon [--original=] [--mapping=] [--build]`. The landing records the sheet and cell of every value into `takeon_blocks` and `takeon_schedule_lines` and runs its gates. The build of `contract_takeon` under the governed `takeon_history_basis` is proposed by one person and approved by another (`takeon_build_requests`; `eir-takeon.build` proposes when nothing is pending and approves the pending request otherwise). A new proposal supersedes a pending one, and an approval is refused when a later workbook has landed since the proposal. Under the recompute basis the build writes the workbook schedule as version 1 (`schedule_source` TAKEON_WORKBOOK), solves the EIR from origination, checks it against the schedule's own rates (`takeon_eir_plausibility`) and rolls the amortised cost forward to 31 July 2024; take-on fees land as PENDING fee lines.

### 4.9 Known data hazards

These come from the client deliveries received between August and October 2026 and must be respected by anyone loading data.

- Extract A carries typed Excel dates whose day and month are swapped (a date entered as day-month was stored as month-day). Text dates in the same columns are correct. Check first repayment and value dates against the disbursement tranche text before trusting a typed date. The reader does not correct this automatically; it flags unparseable values only.
- The Extract C delivered on 26 August 2026 stacks three generation runs. Runs 7 and 25 are identical and run 41 repeats all of 2025, so summing the file triple-counts 2025. Load run 41 only. The import service records the run id as provenance but does not filter on it.
- Trial balance profit and loss balances are cumulative year to date and reset every January. A monthly figure is the difference between consecutive months, with January taken whole. `app/Services/Eir/TrialBalanceMovementService.php` applies this rule on read and never differences balance sheet accounts. The December 2025 monthly file is post-closing and carries no income statement; the pre-closing December balances come from the AFS bridge workbook (`--afs`).
- Twenty-two percent of Extract B rows carry a note that the interest and principal split was estimated by an amortisation formula rather than stored by the core banking system.
- Interest income has no customer grain in the general ledger: the interest GL spools are monthly aggregate journals. Per-loan interest can only come from the loan module extract, never from the ledger.
- E-Banker regenerates a loan's instalment chart when its terms change, so the live chart is only the latest version; earlier versions are in the reschedule history (RS_02a to RS_02d). Some charts date several instalments on one day. Read the chart in force through `InstalmentChartHistory`, never the live rows, for a past month-end.
- Not every write-off is posted with the write-off type: batch TRF 3 of 29 June 2026 cleared status-H loans as repayments with the other leg on GL 1064. Read write-offs through `WriteOffClassifier`, never by transaction type alone.

### 4.10 Reconciliation after a load

Contract Schedule 3 requires record counts to reconcile one hundred percent and aggregate values within 0.1 percent. After a file import, compare the `imports` row counts against the source file, then the Loan Book page totals for the period against the core banking control total. After a pack lands, read its gates on Imports & Feeds, E-Banker Loads, and after a build the differences it printed on Loan Book Builds and the flagged rows on Periods Built. After EIR loads, use the tabs of EIR & Revenue Recognition, EIR Data (Contract Master, Cash Flows, Drawdowns, Reference Rates, Trial Balances, Write-offs, Restructures & Resets, Schedule Review) and of EIR Calculations (Calculations, Blockers, Coverage by Portfolio, Largest Facilities, EIR as at a Date, GL Reconciliation) to confirm that every tape contract has a profile and to see the named blockers.

### 4.11 The client's own loan books against the rebuilt book

`app/Services/Ebanker/ClientBookReconciliationService.php` compares a loan book the client gave for a month-end with the book the system rebuilt for the same month (Client Book Reconciliation Specification v1, 17 October 2026). `ClientBookReader` reads three kinds as received: MAIIC's monthly E-Banker loan book report (`ebanker_report`, the rpt_Loan_Book_Detail_Report in .xls, .xlsx or .csv; columns read by their header, each GL's rows must add up to its printed "GL Wise Total" or the file is refused), the audited December 2025 ECL model's portfolio report values (`audited_model`; accounts masked, so a facility is matched by a balance unique on both sides, else by the normalised customer name and the nearest balance, as `staging:december-check` matches) and the reconciliation template the screen exports for a month (`template`, backfilled with the system's figures; a blank client cell takes no position). A row's day count is the lower bound of the oldest arrears bucket the report fills, or of the model's revised age bracket; the E-Banker report's buckets end at 270 days, so overdue no bucket holds is read as 271 days and the row says so (`days_basis`).

`land()` keeps the file as a supporting document of the book (`approval-documents/client_loan_books/{id}`), its rows in `client_loan_book_rows` and the book in `client_loan_books` (one per month and file hash). `compare()` reads the month's `loan_books` (the loan GLs of `LandingZoneReader::LOAN_GLS`) and stages them under the policy in force (`StagingService::evaluate`), then records each difference in `client_book_differences`: in the client's book only, in the system's book only, an excluded account (for information), a different arrears bracket (the directive's brackets: 0 to 30 days, 31 to 90, 91 to 180, over 180), a different balance (more than K1,000 and half a percent) or a different stage. It writes the differences to `storage/app/client-book-reconciliation/{period} - {book} (book n) differences.csv`. A comparison run again keeps each decision, and a loan an approved override now agrees is marked reconciled. Nothing here writes to the loan book.

`propose()` turns a difference into a staging basis override (source `client_book`, the client's day count) and/or a gross amount override (the client's carrying amount) for that month, links the client's book to each as its evidence (`supporting_document_links`) and refuses a locked month; `keep()` records the system's figure standing with a reason. The overrides are approval workflows (`staging-override`, `gross-override` in `App\Support\Approvals`): the proposer cannot approve, an approval needs a supporting document, and they are on the approvals register. They take effect only when the month is rebuilt (`LoanBookBuildService`), which the screen's "Rebuilds due" proposes. The screen is Customer & Loan Data, Client Book Reconciliation (`ClientBookReconciliationController`, prefix `client-books`). From the command line: `php artisan eir:client-book land|compare|manifest|list`. The bootstrap (step 6.13) lands and compares every book of `docs/bootstrap/client_books/manifest.json`: MAIIC's E-Banker reports of December 2024 to August 2026 and the audited December 2025 model.
